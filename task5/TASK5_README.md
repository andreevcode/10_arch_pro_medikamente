>2. **Parallel run.** Запуск старой и новой системы параллельно для постепенного перевода нагрузки.
>3. **Branch by abstraction.** Постепенный перенос функциональности слой за слоем с использованием абстракций.

>3. **Выявить риски и распределить роли.**
>    * Выявить ключевые риски, связанные с выбранной стратегией. Например, для Parallel run — синхронизация данных, для Branch by abstraction — согласованность версий.

### Часть 1. Анализ текущей ситуации и выбор стратегии миграции

#### 1.1. Контекст и анализ текущей ситуации

Компания «Медикаменте» осуществляет переход от децентрализованной системы ручного учета (файлы Excel, разрозненные инсталляции 1С) к современной микросервисной платформе.

- **Целевая To-Be архитектура:** построена на принципах DDD (домены Patient, Schedule, EMR, Lab), использует отдельные OLTP и OLAP хранилища, в архитектуру заложены принципы Privacy by Design.
- **Ключевые ограничения:** сложность новой инфраструктуры безопасности, сложность слоя интеграции с 1С, низкая толерантность бизнес-пользователей (врачей и администраторов) к изменениям и простоям.

#### 1.2. Обоснование выбора стратегии миграции
Из предложенных вариантов (**High-level design**, **Parallel run**, **Branch by abstraction**) для данного кейса единственно верным и безопасным является **Branch by abstraction (с элементами паттерна Strangler Fig)**.

**Минусы** других вариантов:
- **High-level design:** детализации недостаточно для реализации операционной стратегии миграции.
- **Parallel run:** 
  - ведение двойного учета в Excel и новой системе одновременно приведет к большому росту нагрузки на врачей и другой персонал, а согласно анализу рисков (Задание 4), *«сопротивление персонала»* имеет наивысший приоритет (P1); двойная работа гарантированно спровоцирует саботаж. 
  - кроме того, это создаст конфликты данных (например, двойная запись пациентов на одно и то же время в разных системах).

**Преимущества Branch by abstraction:**
- **Отказ от Big-Bang:** в Задании 4 отказ от одномоментного запуска выделен как мера приоритета P1. Данная стратегия позволяет переносить бизнес-процессы поэтапно. Вместо одного глобального «Дня Х» мы получаем серию управляемых релизов (фаз миграции).
- **Бесшовная интеграция:** использование компонента `ERP Adapter` позволит новой микросервисной платформе общаться с легаси-системой 1С.
- **Изоляция доменов и частичная миграция данных:** 
  - будем запускать сервисы поочередно, перенося только необходимый для них срез данных;
  - например, для запуска системы управления расписанием `Schedule Service` достаточно смигрировать из Excel журналов записи и список пациентов. 
  - затем после стабилизации этого модуля сможем провести следующий Go-Live (и т.д.).

#### 1.3. Основные проблемы и задачи, которые решает Cutover-план
1. **Подготовка чистых данных (Privacy by Design)**: Предварительная ETL-очистка грязных данных из Excel и настройка инструментов Data Governance до начала миграции. Разметка данных (тегирование) и настройка ABAC в Keycloak для защиты конф.данных.
2. **Снижение инфраструктурных рисков**: развертывание компонентов безопасности (Vault, mTLS) и предварительные нагрузочные тестирования до пуска бизнес-трафика.
3. **Управление человеческим фактором**: разделение User Acceptance Testing (UAT) на проверку бизнес-логики и безопасности, а также выделение периодов усиленной поддержки (Hypercare) после каждого микро-релиза для адаптации персонала.

### Часть 4. Пояснения к cut-over плану

#### 4.1. Ключевые риски выбранной стратегии (Branch by abstraction) и меры управления
Использование паттерна `Branch by abstraction` означает, что филиал находящийся в процессе переезда, будет длительное время работать в переходном, гибридном состоянии. Это несет специфические риски, которыми необходимо управлять:
1. **Фрагментация и потеря связности данных:**
    - **Риск:** При пошаговом переносе журналов Excel (сначала журналы записи и списки пользователей) высок риск появления сиротских файлов (Orphan files) и дублирования сущностей;
      - например, из-за возможных проблем с консистентностью идентификаторов ID в старых Excel-журналах.
    - **Меры управления**:
        - Использование строгих алгоритмов дедупликации при первичной миграции данных.
        - Выделение невалидных строк и нераспознанных сканов в карантин (Dead Letter Queue) для ручного разбора бизнес-аналитиком и пользователями до наступления Go-Live.
2. **Усталость от гибридных процессов и человеческий фактор (Риск P1):**
    - **Риск:**
        - На промежуточных этапах сотрудникам придется совершать действия в разных системах.
        - Например, в Фазе 1 ресепшен заносит ПДн в новый портал, но печатает шаблоны и сохраняет сканы на старом сетевом диске. Это вызывает путаницу, сопротивление изменениям и саботаж.
    - **Меры управления:** 
      - Разделение User Acceptance Testing (UAT) на проверку бизнес-флоу и безопасности. 
      - Обучение на живых примерах. 
      - Закладывание длительных периодов усиленной поддержки (Hypercare) длительностью 1-2 недели после каждого микро-релиза для оперативной корректировки UI и процессов.
3. **Рассинхронизация при сосуществовании систем:**
    - **Риск:** При дельта-миграциях или интеграции с 1С возможны сбои передачи данных.
    - **Меры управления:** 
      - Установка жесткого таймаута (допустим 40 минут) на починку дельта-скриптов с готовностью к откату (перевод Excel обратно из Read-Only). 
      - Использование асинхронных очередей с ретраями для связи с 1С.

#### 4.2. Распределение зон ответственности в War Room (Штаб миграции)
* **Технический директор (Release Manager):** Оркестратор cutover-плана. Контролирует тайминг, принимает решения Go/No-Go на контрольных точках, инициирует план отката.
* **SecOps / Администратор сети:** Отвечают за инфраструктуру безопасности (Vault, Istio, Keycloak), проверяют отсутствие "слепых зон" (аудит-логи) и отсутствие утечек данных в UI (проверка маскирования).
* **QA-инженер:** Проводит нагрузочное тестирование на Staging, координирует приемочное тестирование (UAT) с бизнес-пользователями.
* **Бизнес-аналитик (Data Engineer):** Отвечает за ETL-процессы, очистку, миграцию исторических данных в новые БД и S3.
* **Представители бизнеса (Ресепшен, Врачи, Кассиры):** Выполняют сквозные сценарии на этапе UAT, дают обратную связь в период Hypercare, подтверждают бизнес-готовность системы.

#### 4.3. План действий при возникновении инцидентов (Incident Response Plan)
1. **Детекция:** Проблема выявляется через систему алертинга (падение метрик в Grafana/Kibana) или через обратную связь от персонала во время UAT/Hypercare.
2. **Оценка (Triage):** Release Manager совместно с командой оценивает критичность сбоя. Запускается жесткий тайминг (например, 40 минут на попытку горячего исправления — Fix Forward).
3. **Принятие решения:** Если проблема блокирует критический бизнес-процесс (запись пациентов, прием оплат) и не решается в отведенное окно, Release Manager объявляет **No-Go** (или Rollback).
4. **Исполнение отката (Rollback Execution):**
    - Возврат маршрутизации DNS на легаси-интерфейсы.
    - Снятие режима Read-Only со старых баз/Excel.
    -  Запуск скриптов компенсирующих транзакций для согласования данных.
5. **Пост-мортем:** После стабилизации клиники на легаси-системе проводится анализ корневых причин (Root Cause Analysis), вносятся исправления в код/инфраструктуру, и назначается новая дата миграции.
